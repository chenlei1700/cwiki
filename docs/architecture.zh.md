## 1. 问题

LLM 维护的知识库有几种特征性的失败方式，而且出事当天没有一种看起来像失败：

- **复制漂移** —— 同一事实手写在三处；两处过期，读者分不清哪份是现状。
- **上下文成本蠕升** —— 每个会话把自己的教训追加进常驻加载的文档；十八个月后这份文档每轮的开销超过它指导的工作本身。
- **后写的赢** —— 一次订正静默覆盖历史；"曾经存在过分歧"这条信息被销毁。
- **散文态状态** —— "这个方向死了"写成一段没有任何工具能读的文字；该方向之后被昂贵地重新探索。
- **纪律衰减** —— 以上每一条都有书面规则防着，而光有书面规则就会衰减。（这是让其余四种从一次性事故变成反复发作的元失败。）

cwiki 是一个系统的泛化——它在一个多年期生产项目里把五种全踩过一遍，并为每一种长出了对策。

## 2. 核心模型：两根正交轴

每一块内容都在两根彼此独立的轴上分类。文档系统里的多数混乱来自把它们混为一谈。

### 2.1 修改权 —— 谁可以编辑（L1 / L2 / L3）

| 层 | 是什么 | 谁写 |
|---|---|---|
| **L1 SSOT** | 机器生成的原始真相（账本、JSON 产物） | 仅脚本 |
| **L2 Derived** | 从 L1 算出的视图（`_current_*` 摘要） | 仅同步脚本 |
| **L3 Narrative** | 故事、教训、方法论 | 仅人类 + LLM |

铁律：**一个事实只活在一个地方，在 L1**；其余一切用链接。L2 整页重生成、从不合并；L3 永不被脚本覆盖。这一条规则移除了整个复制漂移失败类（完整规范：SCHEMA §3）。

### 2.2 注入档位 —— 带着它要花多少钱（T0–T3）

| 档 | 何时加载 | 住在哪 |
|---|---|---|
| T3 | 每个会话的每一轮 | `CLAUDE.md`：规则、指针、一行教训 |
| T2 | skill/话题激活时 | skill 正文、concepts 页 |
| T1 | 被显式查询时 | wiki 页、归档 |
| T0 | 仅工具查询 | 原始账本 |

经典病是 **T1 内容住在 T3 价位**——战记长文贴进 `CLAUDE.md`。蒸馏回路（SCHEMA §13）持续把内容向下重新归档；预算线和单条形态闸让归错档的写入第二天早上就被点名。

两根轴正交：一条叙事教训（L3）可以被错放在 T3；一份派生视图（L2）刻意贴近 T3——因为它又小又新。

## 3. 一个被 cwiki 管理的项目长什么样

```
project/
├── CLAUDE.md               # T3: 规则 + 指针（有预算、有单条形态闸）
├── wiki/
│   ├── SCHEMA.md           # 这个 wiki 运行于其下的规则
│   ├── index.md            # 每次查询的入口
│   ├── log.md              # 一行一事件，新的在前
│   ├── MAINTENANCE_ROUTING.md  # 事件 → 待更新文件 路由表
│   ├── concepts/ experiments/ sources/ architecture/ <domain>/   # L3 页面
│   ├── _topics.json        # 话题注册表（缝合键）                 [§16]
│   ├── _tombstones.json    # 已删页注册表                        [§15]
│   └── <topic>_ledger/     # 住在 wiki 里的 L1 机器数据           [§10]
└── scripts/maintenance/    # 拷来的工具: lint、同步、漂移检测
```

信息在一个回路里流动：

```
   人 / LLM 会话 ──写──► L3 叙事 ──链接──► L1 真相
   自动生产者 ──追加──► L1 账本 ──同步──► L2 视图
   夜间任务 ── 重生成 L2，跑 lint + 漂移检测，追加当日 L1
   闸门（pre-commit / hooks / 夜检 exit code）── 拦截或点名违规
```

四股力量维持一致性：同步脚本、写入时闸门、夜间任务、以及机械检查看不见之处的周期性 LLM lint。

## 4. 方法论，浓缩成七条承诺

1. **链接强制的单一真相。** 事实只活一次；其余全是指针。此规则越出 wiki —— `CLAUDE.md`/`README` 链接派生视图而不是抄它的数字。
2. **纪律变闸门。** 复盘产出的任何"下次记得……"都翻译成一个会失败的检查（pre-commit、hook、带 exit code 的夜检、测试）。写成散文的规则会衰减；接成红色检查的同一条规则不会。三条子规则，各自付过事故学费：每个闸门故障注入验一次；白名单从消费方导出而不是手写；报证据、不报布尔。
3. **守门员也要被守。** lint 自己的结果进夜间报告；每个检查带 `--selftest`（含故障注入）并跑在项目的常规测试套件里。静默崩掉的闸门比没有闸门更糟。
4. **历史只追加；状态结构化。** 订正是替代行/overlay，从不原地改。废弃/关闭是机器可读标记（frontmatter、账本列、墓碑），从不只是散文。矛盾先落专区，*然后*才改正文。
5. **不回溯采纳。** 每个闸门都钉一个 cutoff 日期；历史内容豁免、渐进迁移（on-touch + 积压队列）。首日对历史执法会杀死采纳——宽限胜过洁癖。
6. **按痛扩容。** 核心（§1–§8：分层、页面、交叉引用、Ingest/Query/Lint）是首日件。每个规模件（§9–§16）写明它所对治的痛，痛没出现前保持休眠。上来全装是文档写明的反模式。
7. **LLM 整理，机制核验。** 人喂材料、做决定；LLM 组织、交叉链接；但凡 LLM 的*宣称*有分量之处（一次迁移"成功了"、一个页面"存在"），都有机械检查核验——安全模型里不含信任，对 LLM 自己的输出也一样。

## 6. 一个被管项目的生命周期

1. **第 0 天 —— Bootstrap 或 Adoption。** 全新项目：5 分钟骨架（skill.md §2）。既有项目：只读盘点 → 确认 adoption map → 骨架共存 → 渐进迁移，采纳日 = cutoff（skill.md §2B）。
2. **每天 —— Ingest / Query / Lint。** 材料带双向交叉引用进页面；查询从 `index.md` 起步；lint 只报告、从不自动改。
3. **痛出现时 —— 规模件。** 多文件事件老被做一半 → 路由表；生产/消费方过 10 个 → frontmatter 执法；"这个试过没有"没法回答 → 账本；账本结论没人看见 → 生成页；常驻文档膨胀 → 预算/蒸馏；并发会话模糊了新旧 → 指纹/墓碑；"关于 X 的一切在哪" 没有入口 → 话题层。
4. **每夜 —— 自愈。** L2 重生成，lint 与漂移检测带 exit code 跑，迁移批次推进，流水线报告记录守门员自己有没有跑。

## 7. 出处与局限

方法论蒸馏自一个多年期量化研究项目（40+ skills、夜间流水线、10⁵–10⁶ 行的账本），并吸收了对 TencentDB-Agent-Memory 与 NVIDIA auto-ontology 的调研；这里的每样东西都经受过生产接触，若干条规则之所以存在，正是因为它们的缺席在上游造成过有名有姓的事故。

已知局限，写明而非粉饰：语义级重复（抄的是*论断*而不是数字）机器检测不了——若能被抓，是在蒸馏抽查比读那一关；订正回标只有提示级 lint；写入侧终究运行在 LLM 纪律之上——这正是每条写入侧规则都配"次日检测闸"而非"承诺"的原因。
