# How the wiki stays alive — management, sync & update mechanisms

This document describes the full operating machinery behind an LLM-maintained wiki, distilled from a multi-year quant research project where the system runs in production (40+ skills, nightly pipelines, append-only ledgers with ~10⁵–10⁶ rows). The templates in `templates/` give you the *rules*; this document gives you the *moving parts* that keep the rules true over months.

Everything here is incremental: a fresh project needs only Mechanism 0. Each later mechanism states the pain that justifies adopting it.

---

## The picture

```
            humans / LLM sessions                automated producers
                   │                                     │
          (hand-write L3 narrative)           (write L1 ledgers & JSON)
                   │                                     │
                   ▼                                     ▼
   ┌───────────────────────────────────────────────────────────────┐
   │                           wiki/                               │
   │  L3 narrative   ◄─ references ─  L1 SSOT  ─ sync ─►  L2 views │
   │  concepts/ experiments/ log.md   *.jsonl, JSON     _current_* │
   └───────────────────────────────────────────────────────────────┘
                   ▲                                     ▲
                   │                                     │
        gates & hooks (block bad writes)      nightly jobs (regenerate,
        pre-commit / PostToolUse / Stop        detect drift, lint)
```

Four forces keep it consistent:

1. **Sync scripts** regenerate L2 from L1 (same fact never copied by hand)
2. **Hooks/gates** block the writes that would violate layering, at the moment they happen
3. **Nightly jobs** regenerate views, append daily L1 data, and run drift detectors
4. **Lint** (LLM-driven, periodic) catches what mechanical checks can't

---

## Mechanism 0 — manual trio: Ingest / Query / Lint

This is the baseline from `skill.md` §3–§5 and needs no automation: the LLM routes new material to pages, answers questions from the index, and periodically health-checks. Everything below exists to keep Mechanism 0 honest as the project grows.

---

## Mechanism 1 — the L1→L2 sync script

**Pain that justifies it**: a "current state" summary (current release, current config, headline metrics) that humans keep re-typing — and that is wrong within two weeks.

**Contract** (reference skeleton: [`tools/sync_views_example.py`](../tools/sync_views_example.py)):

- Reads only L1 (an append-only ledger + machine-produced run artifacts). Never reads L3.
- Rewrites the L2 file **completely** — no merging, no preserving. L2 files are owned by the script.
- First line of every L2 file: an explicit marker
  `<!-- AUTO-GENERATED by sync_views.py — DO NOT EDIT BY HAND -->`
- Three modes:
  - default: regenerate (overwrite)
  - `--check`: regenerate in memory, compare to disk, **exit 1 if stale** — wire this into pre-commit so a stale L2 can never be committed
  - `--dry-run`: print what would be written
- Runs at least nightly (see Mechanism 4), so even if nobody commits, views self-heal within a day.

**Corollary for CLAUDE.md / README**: these files are L2 *consumers*. They link to the derived view; they never carry its numbers. This single rule removed an entire class of "the docs say version X but production runs Y" bugs.

## Mechanism 2 — append-only ledgers + query-before-explore

**Pain**: "didn't we try this six months ago?" — and nobody can prove it, so it gets tried again.

Two ledgers, both L1, both append-only JSONL:

| Ledger | Records | Appended when |
|---|---|---|
| `release_history.jsonl` | what actually shipped (version, parent, delta, links to artifacts) | every release |
| `hypothesis_history.jsonl` | **every exploration, win or lose**: hypothesis text, what changed, result, failure reason, lesson links | every completed exploration |

Operating rules:

1. **Append-only is absolute.** A wrong row is corrected by appending a superseding row (or an overlay record with a new key that consumers explicitly honor) — never by editing history. Once several tools read the ledger, in-place edits silently desynchronize them.
2. **Query before explore.** Every exploration-type workflow starts with `query_ledger --topic X --result fail`. This is the highest-ROI habit in the whole system.
3. **Record the *reason*, not just the verdict.** "Closed because unmeasurable" and "closed because it doesn't work" lead to opposite future decisions; a bare `fail` flag collapses them.
4. **Retirement is structured.** Closing a whole direction writes a machine-readable `action: close` record. Prose conclusions are invisible to coverage tools, and "invisible to the tool" degrades into "reported as never tried" — which is how directions get expensively re-explored.

## Mechanism 3 — dependency frontmatter + four enforcement layers

**Pain**: "changed X, forgot to update Y" across 10+ skills/scripts that read and write wiki content; hand-maintained reverse-mapping tables that are always behind.

Design (full spec: templates/SCHEMA.md §9): executable docs declare `consumes / produces / upstream_skills / downstream_skills / load_bearing_for` in frontmatter; everything derived (reverse tables, dependency graphs) is script-generated and DO-NOT-EDIT.

The declarations only stay true because enforcement is **four-layered** — each layer backstops the one before:

| Layer | Mechanism | Tool | Fires |
|---|---|---|---|
| A | Written rule in CLAUDE.md / SCHEMA | — | session start (read) |
| B | PostToolUse hook: on skill-file creation, print a **draft frontmatter** to stderr so compliance costs one paste | `tools/scan_skill_dependencies.py --skill <name> --print` | instant of creation |
| C | Stop hook: block session end if a *newly created* skill lacks the fields (legacy files exempt — don't block migration) | `tools/check_new_skills_registered.py` | session end |
| D | Nightly drift detector: unregistered recent files (grace period), declarations pointing at paths/tables that no longer exist (hard error, exit 1), asymmetric reverse declarations (info only) | `tools/check_dependency_drift.py` | nightly |

Hook wiring example (`.claude/settings.json`):

```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Write",
      "hooks": [{ "type": "command",
        "command": "python scripts/maintenance/nudge_skill_frontmatter.py" }]
    }],
    "Stop": [{
      "hooks": [{ "type": "command",
        "command": "python scripts/maintenance/check_new_skills_registered.py" }]
    }]
  }
}
```

Two hard-won design rules:

- **Severity separation**: dead references = hard error (exit 1, someone must fix today); asymmetry = info (self-heals as declarations accrue). Mixing severities trains people to ignore the report.
- **Grace periods for legacy**: enforcement applies strictly to *new* files; the existing backlog migrates gradually under layer D warnings. Blocking everything on day one kills adoption.

## Mechanism 4 — nightly automation & freshness detection

**Pain**: daily-produced knowledge (market state, health reports, metrics) that goes stale the first day someone forgets to run a script.

Pattern: a nightly pipeline (cron / EOD job) with **numbered stages**, several of which write into the wiki:

- stages that append daily L1 JSON (e.g. `wiki/<topic>/YYYYMMDD.json` + a `latest.json` L2 pointer)
- a stage that re-runs the L1→L2 sync (Mechanism 1) — the self-healing pass
- a stage that runs the drift detector (Mechanism 3, layer D)
- domain health checks that write state machines (`state.json`) consumed by next-day jobs

Rules that keep the pipeline honest:

1. **Freshness checks are tiered**: P0 = artifact missing (fix now), P1 = artifact older than ~36h (investigate), P1 = source data newer than derived data (producer silently skipped). Each tier names its fix command.
2. **Experimental stages are gated soft-fail**: a stage for a not-yet-production feature logs a warning and continues; it must never block the stages real operations depend on. Promote to hard-fail only when the feature ships.
3. **Independent stages get independent timeouts**: never nest a slow new job inside an existing stage's timeout budget — that's how both die together and the death is misattributed.
4. **"Configured ≠ in effect"**: any long-lived process (worker, server) locks code and config at startup. Every routing-table event that changes config ends with "restart these processes", and a next-day verification step confirms the change is actually live.

## Mechanism 5 — generated wiki pages over machine ledgers

**Pain**: conclusions that exist only in machine ledgers (10⁵+ rows) are invisible to humans; directions already judged dead get re-opened because no page said so.

Pattern (spec: templates/SCHEMA.md §10–§11): a generator renders per-topic summary pages from the ledger into the wiki, under three rules —

1. **Format derives from the wiki's existing page types** — a generated summary looks like an experiment page, not a new invented format per generator.
2. **Regenerate-without-clobber** — hand-written verdict sections survive re-runs. A generator that wipes human input on run #2 stops being used (and then the pages rot, which is worse than never existing).
3. **Self-disclosure** — a generated page states what its own emptiness means ("no decision records ≠ nobody tried; records may predate structured markers"). An empty section without this note reads as an authoritative "nothing happened", which is precisely the misreading these pages exist to prevent.

Division of labor worth writing on the page itself: *the ledger answers "how did this specific item do"; the wiki page answers "is this direction still worth opening"*.

## Mechanism 6 — discipline becomes gates

The meta-mechanism behind all of the above. Observed repeatedly: **a rule written as prose decays; the same rule wired as a failing check doesn't.** Whenever a post-mortem produces a "next time remember to…", translate it into one of:

- a pre-commit check (`sync --check`, large-file guard, lint subset)
- a session hook (PostToolUse nudge, Stop block)
- a nightly detector with an exit code
- a test that fails loudly

Three rules for the gates themselves, each paid for in incidents:

1. **Fault-inject every gate once**: re-introduce the original bug and confirm the gate actually turns red. A gate that has never fired is indistinguishable from a broken one.
2. **Derive allow-lists from the consumer, don't hand-write them**: any hand-maintained list of "valid fields / files / events" is already behind the consumer it describes. Export it from the consuming code, or assert against the consumer's real query.
3. **Report evidence, not booleans**: a drift report that prints *which* reference broke and *what the fix command is* gets acted on; a bare "3 violations" gets ignored.

## Operations calendar

| Cadence | What runs | Mechanism |
|---|---|---|
| On write (hooks) | frontmatter nudge; Stop-block for unregistered new skills | 3B, 3C |
| On commit (pre-commit) | `sync --check` (stale L2 blocks commit); large-file guard | 1, 6 |
| Nightly | daily L1 appends; sync regenerate; drift detector; freshness tiers | 2, 1, 3D, 4 |
| On release (routing E5) | ordered checklist + safety nets + process restarts | routing table |
| Weekly / on demand | LLM Lint (orphans, dangling links, stale tentative, duplicate facts) | 0 |

## Failure-mode index

| Symptom | Likely cause | Where to look |
|---|---|---|
| "Current state" doc contradicts reality | sync not run / someone hand-edited L2 | Mechanism 1; pre-commit `--check` |
| Same metric differs across two pages | fact copied instead of linked | SCHEMA §3 cardinal rule |
| Re-running an experiment that already failed | exploration ledger not queried (or failure never appended) | Mechanism 2 |
| "Changed X, downstream Y silently broke" | missing/stale frontmatter declaration | Mechanism 3, drift report |
| Daily JSON stopped updating, nobody noticed | no freshness tiers on that artifact | Mechanism 4 |
| Config change "didn't take effect" | long-lived process never restarted | Mechanism 4, rule 4 |
| Generated page wiped human notes | generator missing clobber protection | Mechanism 5 |
| A direction everyone 'knows' is dead gets re-explored | verdict existed only as prose / only in ledger | Mechanisms 2.4 + 5 |
