# wiki 如何保持活着 —— 管理、同步与更新机制

> 中文（默认） | [English](maintenance-mechanisms.md) — 如有出入以英文版为准。

本文描述 LLM 维护型 wiki 背后的完整运转机器，蒸馏自一个多年期量化研究项目的生产系统（40+ skills、夜间流水线、10⁵–10⁶ 行的 append-only 账本）。`templates/` 给你的是*规则*；本文给你的是让规则在数月里保持为真的*运动部件*。

这里的一切都是增量的：全新项目只需要 Mechanism 0，之后每个机制都写明了采纳它的那种痛。

---

## 全景图

```
            人 / LLM 会话                          自动生产者
                 │                                     │
         （手写 L3 叙事）                   （写 L1 账本与 JSON）
                 │                                     │
                 ▼                                     ▼
   ┌───────────────────────────────────────────────────────────────┐
   │                           wiki/                               │
   │  L3 叙事   ◄─ 引用 ─  L1 SSOT  ─ 同步 ─►  L2 视图              │
   │  concepts/ experiments/ log.md   *.jsonl, JSON     _current_* │
   └───────────────────────────────────────────────────────────────┘
                 ▲                                     ▲
                 │                                     │
      闸门与 hooks（拦截坏写入）            夜间任务（重生成、
      pre-commit / PostToolUse / Stop       漂移检测、lint）
```

四股力量维持一致：

1. **同步脚本**从 L1 重生成 L2（同一事实永不手抄）
2. **hooks/闸门**在违规写入发生的瞬间拦截它
3. **夜间任务**重生成视图、追加当日 L1、跑漂移检测
4. **Lint**（LLM 驱动、周期性）兜住机械检查看不见的部分

---

## Mechanism 0 —— 手动三件套：Ingest / Query / Lint

即 `skill.md` §3–§5 的基线，不需要任何自动化：LLM 把新材料路由进页面、从索引答题、周期性体检。下面的一切都是为了在项目长大后让 Mechanism 0 保持诚实。

---

## Mechanism 1 —— L1→L2 同步脚本

**对治的痛**：一份"当前状态"摘要（当前版本、当前配置、头条指标）被人反复手打——两周内必然失真。

**契约**（参考骨架：[`tools/sync_views_example.py`](../tools/sync_views_example.py)）：

- 只读 L1（append-only 账本 + 机器产物）。永不读 L3。
- **整页重写** L2 文件——不合并、不保留。L2 归脚本所有。
- 每份 L2 首行是显式标记：`<!-- AUTO-GENERATED by sync_views.py — DO NOT EDIT BY HAND -->`
- 三种模式：默认 = 重生成（覆盖）；`--check` = 内存重生成后与磁盘比对，**过期则 exit 1**——接进 pre-commit，过期的 L2 永远提交不进去；`--dry-run` = 只打印将写什么。
- 至少每夜跑一次（见 Mechanism 4），没人提交也会在一天内自愈。

**对 CLAUDE.md / README 的推论**：它们是 L2 的*消费方*——链接派生视图，永不携带其数字。这一条消灭了整类"文档说版本 X、生产跑的是 Y"的 bug。

## Mechanism 2 —— append-only 账本 + 探索前先查账

**痛**："这个半年前是不是试过？"——没人能证明，于是又试一遍。

两本账，都是 L1、都是 append-only JSONL：

| 账本 | 记录 | 何时追加 |
|---|---|---|
| `release_history.jsonl` | 真正发布过什么（版本、父版本、差量、产物链接） | 每次发布 |
| `hypothesis_history.jsonl` | **每一次**探索，无论输赢：假设原文、改了什么、结果、失败原因、教训链接 | 每次探索完成 |

运行规则：

1. **append-only 是绝对的。** 错误的行用追加替代行（或消费方显式认的 overlay 记录）订正——永不改历史。一旦有 N 个工具在读账本，原地改就会把它们全部静默去同步。
2. **先查账再探索。** 每个探索型工作流以 `query_ledger --topic X --result fail` 开场。这是全系统投入产出比最高的一个习惯。
3. **记"为什么"，不只记判决。** "因为量不出来而关闭"与"因为没效果而关闭"导向相反的未来决策；一个光秃秃的 `fail` 标志把两者压扁了。
4. **退役是结构化的。** 关闭整个方向要写机器可读的 `action: close` 记录。散文结论对覆盖统计工具不可见，而"工具看不见"会退化成"被报告为从未尝试"——方向就是这样被昂贵地重新探索的。

## Mechanism 3 —— 依赖 frontmatter + 四层执法

**痛**：10+ 个读写 wiki 的 skills/脚本之间"改了 X 忘了 Y"；手工维护的反向映射表永远落后。

设计（完整规范 templates/SCHEMA.md §9）：可执行文档在 frontmatter 声明 `consumes / produces / upstream_skills / downstream_skills / load_bearing_for`；一切派生物（反向表、依赖图）由脚本生成、DO-NOT-EDIT。

声明之所以保持为真，靠的是**四层执法**——层层互为兜底：

| 层 | 机制 | 工具 | 触发时机 |
|---|---|---|---|
| A | CLAUDE.md / SCHEMA 里的书面规则 | — | 会话启动（被读到） |
| B | PostToolUse hook：skill 文件创建瞬间向 stderr 打出**frontmatter 草稿**，合规成本降到一次粘贴 | `tools/scan_skill_dependencies.py --skill <name> --print` | 创建瞬间 |
| C | Stop hook：*本会话新建的* skill 缺字段则拦截会话结束（legacy 文件豁免——不阻塞渐进迁移） | `tools/check_new_skills_registered.py` | 会话结束 |
| D | 夜间漂移检测：未注册的新文件（宽限期）、指向已不存在路径/表的声明（硬错误 exit 1）、反向声明不对称（仅 info） | `tools/check_dependency_drift.py` | 每夜 |

hook 接线示例（`.claude/settings.json`）：

```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Write",
      "hooks": [{ "type": "command",
        "command": "python scripts/maintenance/nudge_skill_frontmatter.py" }]
    }],
    "Stop": [{
      "hooks": [{ "type": "command",
        "command": "python scripts/maintenance/check_new_skills_registered.py" }]
    }]
  }
}
```

两条用事故换来的设计规则：

- **严重度分离**：死引用 = 硬错误（exit 1，今天必须有人修）；不对称 = info（随声明积累自愈）。混在一起会训练人忽略整份报告。
- **legacy 宽限**：执法只对*新*文件严格；存量在 D 层警告下渐进迁移。首日全面拦截会杀死采纳。

## Mechanism 4 —— 夜间自动化与新鲜度检测

**痛**：日产知识（市场状态、健康报告、指标）在某人第一次忘跑脚本的当天就开始腐烂。

模式：带**编号阶段**的夜间流水线（cron / EOD 任务），其中若干阶段写入 wiki：

- 追加当日 L1 JSON 的阶段（如 `wiki/<topic>/YYYYMMDD.json` + 一个 `latest.json` L2 指针）
- 重跑 L1→L2 同步的阶段（Mechanism 1）——自愈通道
- 跑漂移检测的阶段（Mechanism 3 D 层）
- 写状态机（`state.json`）供次日任务消费的领域健康检查

让流水线保持诚实的规则：

1. **新鲜度检查分级**：P0 = 产物缺失（现在修）；P1 = 产物超过 ~36h（去查）；P1 = 源数据比派生数据新（生产者被静默跳过）。每级写明修复命令。
2. **实验性阶段软失败**：未上生产的功能阶段只记警告继续走，永不阻塞真实运维依赖的阶段。功能 ship 后才升级为硬失败。
3. **独立阶段独立超时**：永不把慢的新任务嵌进既有阶段的超时预算——那是两者一起死、死因还被记错的标准路径。
4. **"配置了 ≠ 生效了"**：长活进程（worker、server）在启动时锁定代码与配置。每个改配置的路由表事件都以"重启这些进程"收尾，并有次日核验步确认改动真的活了。

## Mechanism 5 —— 覆盖在机器账本之上的生成页

**痛**：只存在于机器账本（10⁵+ 行）里的结论对人不可见；已被判死的方向因为没有任何页面这么说而被重新打开。

模式（规范：templates/SCHEMA.md §10–§11）：生成器把账本渲染成 wiki 内的逐主题摘要页，守三条规则——

1. **格式沿用 wiki 既有页面类型**——生成的实验摘要长得像实验页，不为每个生成器发明新格式。
2. **重生成不覆盖人写段**——手写判语段落在重跑后存活。第二次运行就抹掉人类输入的生成器会直接没人用（然后页面腐烂，比从未存在更糟）。
3. **自述空态**——生成页必须说明自己的"空"意味着什么（"没有决策记录 ≠ 没人试过——记录可能早于结构化标记；查 <来源>"）。否则空区块读起来像权威的"什么都没发生"，恰是这些页面要防的那种误读。

值得写在页面上的分工：*账本回答"这个具体条目表现如何"；wiki 页回答"这个方向还值不值得开"*。

## Mechanism 6 —— 纪律变闸门

以上一切背后的元机制。反复观察到：**写成散文的规则会衰减；接成失败检查的同一条规则不会。** 每当复盘产出一句"下次记得……"，就把它翻译成以下之一：

- 一个 pre-commit 检查（`sync --check`、大文件闸、lint 子集）
- 一个会话 hook（PostToolUse 提示、Stop 拦截）
- 一个带 exit code 的夜间检测
- 一个会大声失败的测试

对闸门本身的三条规则，各自付过事故学费：

1. **每个闸门故障注入一次**：重新引入它要抓的那个 bug，确认闸门真的变红。从没红过的闸门与坏了的闸门无法区分。
2. **白名单从消费方导出，不手写**：任何手工维护的"合法字段/文件/事件"清单，天生落后于它所描述的消费方。从消费代码导出，或直接对消费方的真实查询做断言。
3. **报证据，不报布尔**：打出*哪条*引用断了、*修复命令是什么*的漂移报告会被执行；一句"3 处违规"会被忽略。

## Mechanism 7 —— 蒸馏回路（上下文预算）

**痛**：常驻加载的 `CLAUDE.md` 长到 harness 舒适注入量的 3 倍——因为每个会话都以常驻价位追加了自己的战记。（源项目实测：329KB → 两批蒸馏后 111KB；目标稳态 ~50KB。）

运动部件（规范：templates/SCHEMA.md §13）：

1. **预算线**，每份常驻文档两条（教训区预算 + 低于 harness 警告线的全文件预算），每夜检查。数字是钉下来的判断值——配置注释里就这么写。
2. **单条形态闸**：cutoff 日期之后新增的 dated 条目必须是"一行 + 指针"（对单条设字节上限）。不回溯——历史归蒸馏积压，首日对历史执法会杀死采纳。这让一条归错档的 3KB 条目第二天早上就被点名；只靠总量线它能藏好几个月。
3. **蒸馏 SOP 只交互跑、永不无头跑**——它做的是编辑判断（什么是 caveat、什么是废话）。每次退役记账（`distill_ledger.jsonl`）；**抽查比读**随机抽 2 条原文与合成页对读，是人工关：合成丢掉 caveat 是静默失败，因为归档存在但没人读归档。
4. 退役有**两档**——独立成段的片段变成指针 + 归档原文；深嵌在复合叙事里的片段只合成、原文不动（整条退役时吸收）。处处强制第一档会绞碎叙事；处处第二档则文件永远不缩。

## Mechanism 8 —— 外部 assistant-memory 的存储主权

**痛**：助手的私有 memory 目录（不进 git、不可浏览、重装即丢）积累了别处都没有的独有事实——一个握着真知识的单点故障。

**原则：事实住 wiki；外部 memory 只放一个指针 + 几行"怎么用"。** memory 是为召回而设的缓存，不是存储之所。

存量积压的迁移可以用无头 LLM 驱动器自动化，但**安全归驱动器所有，不归 LLM**——灌进提示词的 memory 原文按*不可信数据*对待（防注入不建立在信任上，哪怕那是你自己写的文字）：

1. **先备份**——任何动作之前把原文拷进 git 跟踪的文件夹；每次迁移可逆。
2. **机械验收**——LLM 的"MIGRATED"宣称不算数。驱动器核验：宣称的页路径匹配**白名单正则**（仅 wiki 三个目录，无路径穿越、无异常字符）；页面存在；页面字节 ≥ 原文的一个保真下限（防摘要化——事实要存活，不是被概括）；memory 文件被重写为限长指针且 frontmatter 完好。
3. **写入面 delta 闸**——LLM 运行前后各拍一次 `git status` + memory 目录快照；*看护面*（wiki + 代码目录，豁免其他进程夜间会写的机器 churn 子树）内除宣称页之外的任何变化、或目标之外的任何 memory 文件变动 ⇒ 本次失败并点名越界路径。宣称"SKIPPED"同样过闸。已知盲区（写明并接受）：运行前就已 dirty 的文件被再次编辑不会出现在状态集合差里。
4. **失败 ⇒ 从备份回滚 + 可见地标 failed。** 每晚 2-3 个小文件的批次几周清完积压；大文件留给交互会话（质量优先于吞吐）。

## 运维日历

| 节奏 | 跑什么 | 机制 |
|---|---|---|
| 写入时（hooks） | frontmatter 提示；未注册新 skill 的 Stop 拦截 | 3B, 3C |
| 提交时（pre-commit） | `sync --check`（过期 L2 拦提交）；大文件闸 | 1, 6 |
| 每夜 | 当日 L1 追加；同步重生成；漂移检测；新鲜度分级；机械化 wiki lint（预算、单条形态、指纹、墓碑、话题、巨型未跟踪文件——见 `tools/wiki_lint_skeleton.py`）；memory 迁移批次 | 2, 1, 3D, 4, 7, 8 |
| 发布时（路由 E5） | 有序 checklist + 安全网 + 进程重启 | 路由表 |
| 超预算时 | 交互式蒸馏 SOP + 抽查比读 | 7 |
| 每周 / 按需 | LLM Lint（孤儿页、死链、过期 tentative、重复事实） | 0 |

**守门员也要被守**：夜间 lint 自己的结果进流水线报告（崩掉的 lint 是可见的，不是静默的）；每个检查都带 `--selftest` 故障注入并跑在项目的常规测试套件里——谁改坏了判据，得到的是红色测试，而不是一个安静的绿色夜晚。

## 故障模式索引

| 症状 | 可能根因 | 去哪看 |
|---|---|---|
| "当前状态"文档与现实矛盾 | 同步没跑 / 有人手改了 L2 | Mechanism 1；pre-commit `--check` |
| 同一指标在两页数值不同 | 事实被复制而非链接 | SCHEMA §3 铁律 |
| 重跑了一个早已失败的实验 | 探索账本没查（或失败从没记进去） | Mechanism 2 |
| "改了 X，下游 Y 静默坏了" | frontmatter 声明缺失/过期 | Mechanism 3，漂移报告 |
| 日更 JSON 停了没人发现 | 该产物没挂新鲜度分级 | Mechanism 4 |
| 配置改了"没生效" | 长活进程没重启 | Mechanism 4 规则 4 |
| 生成页抹掉了人写的笔记 | 生成器缺覆盖保护 | Mechanism 5 |
| 人人"都知道"已死的方向被重新探索 | 判决只存在于散文/只存在于账本 | Mechanism 2.4 + 5 |
| `CLAUDE.md` 持续膨胀；会话每轮为它买单 | 内容归错档（原子事实住在常驻价位） | Mechanism 7；SCHEMA §13 |
| 两页对现状说法不一、看起来都权威 | 没有 supersedes/墓碑，新旧靠感觉判 | SCHEMA §15 排序 |
| 删掉的页又出现了 | 生成器从没查过墓碑注册表 | SCHEMA §15.2 复活检测 |
| 独有事实只活在 assistant memory 里 | 存储主权没执行 | Mechanism 8 |
| 无头迁移"成功了"但页面是份摘要 | 验收轻信了 LLM 的宣称 | Mechanism 8.2 保真下限 |
