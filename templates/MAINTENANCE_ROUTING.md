# Maintenance Routing Table — <PROJECT_NAME>

> For each recurring **event** that touches the wiki, which files must be updated and how. This is the "file housekeeper" execution manual. Companion: [SCHEMA.md §3](SCHEMA.md) (data layering).

## Why a routing table?

When a single LLM session decides "where does this info go", three failure modes appear:
1. **Stale**: important pages don't get updated session-over-session
2. **Duplicate**: the same fact lands in 3 places, updated in 1, contradictions appear
3. **Lost**: insights end up in transient task lists and disappear next session

Codifying each event → file-list mapping prevents this.

## How to add a new event

When you notice "this kind of change keeps requiring updates to the same group of files", add an `### E<N>` section below with a table:

```markdown
### E<N>. <Event name>

| File | Layer | How to update | Mandatory? |
|---|---|---|---|
| path/to/file | L1/L2/L3 | hand-write / auto-generated by <script> | ✅ / — |
```

### Columns to add as the table matures

Two extra columns earn their keep once an event has ever been executed incompletely:

| Column | What it records | Why |
|---|---|---|
| **Symptom if skipped** | The observable failure when this row is omitted (e.g. "summary shows `?`", "tool reports 'unknown table' and misleads") | Turns the table into a diagnostic index: when that symptom appears later, grep this column |
| **Backstop** | Which automated check catches the omission, if any | Makes explicit which rows have *no* safety net and therefore deserve the most care |

### Multi-step events: ordered checklist + safety nets

When an event is a *sequence* (release, migration, cutover), don't stop at the file table — add:

1. A **numbered step list in strict order**, with the reason ordering matters noted inline (e.g. "append ledger BEFORE running sync — sync derives from the ledger").
2. An **automatic safety-nets block**: which nightly/CI checks catch which skipped step. Safety nets are *backstops, not replacements* — say so explicitly, or the checklist erodes.
3. A final step for **runtime actors**: long-lived processes lock their code/config at startup; a config change is not live until the process restarts. List every process that must be restarted, or the event ends in "configured but not in effect".

## Example events (starter set — customize for your project)

### E1. Adding a new concept to `wiki/concepts/`

| File | Layer | How to update | Mandatory? |
|---|---|---|---|
| `wiki/concepts/<name>.md` | L3 | Hand-write per template | ✅ |
| `wiki/index.md` | L3 | Add one line under Concepts | ✅ |
| `wiki/log.md` | L3 | Append `## [date] add | concept <name>` | ✅ |
| Pages that should reference this concept | L3 | Add `[[concepts/<name>]]` cross-references | ✅ (if any apply) |

### E2. Ingesting external material to `wiki/sources/`

| File | Layer | How to update | Mandatory? |
|---|---|---|---|
| `wiki/sources/<short-name>.md` | L3 | Hand-write summary (NOT a paste) | ✅ |
| `wiki/index.md` | L3 | Add one line under Sources | ✅ |
| `wiki/log.md` | L3 | Append `## [date] ingest | <name>` | ✅ |
| Related concept/architecture pages | L3 | Add `[[sources/<name>]]` where the material informs them | ✅ (if any) |

### E3. Completing an experiment / refactor / incident

| File | Layer | How to update | Mandatory? |
|---|---|---|---|
| `wiki/experiments/<topic>_YYYYMMDD.md` | L3 | Hand-write full report | ✅ |
| `wiki/index.md` | L3 | Add one line under Experiments | ✅ |
| `wiki/log.md` | L3 | Append `## [date] experiment | <one-line conclusion>` | ✅ |
| Affected `architecture/*.md` pages | L3 | Update if the experiment changed system design | ✅ (if applicable) |
| Affected `concepts/*.md` pages | L3 | Update if the experiment produced a new lesson | ✅ (if applicable) |
| Exploration ledger (if adopted, SCHEMA §10) | L1 | Append one row — **win or lose, both get recorded** | ✅ |

> **Ledger on failure too**: the version-history ledger records only what shipped; the *exploration* ledger records every attempt with its hypothesis and failure reason. Before starting any new exploration, query it ("has this been tried? why did it fail?") — this is the single cheapest way to stop a project from re-running dead-end experiments every few months.

### E4. Deprecating or removing content

| File | Layer | How to update | Mandatory? |
|---|---|---|---|
| Old page itself | L3 | Mark `**Status**: deprecated, see [[replacement]]` — do NOT delete unless truly obsolete | ✅ |
| Pages pointing to the old page | L3 | Update `[[]]` references to point to the replacement | ✅ |
| `wiki/index.md` | L3 | Move entry under a "Deprecated" subsection or remove | ✅ |
| `wiki/log.md` | L3 | Append `## [date] deprecate | <name> → <replacement>` | ✅ |
| Skills whose `consumes:` referenced the old page | frontmatter | `grep -l "<old path>" .claude/skills/*/skill.md`, repoint, re-run drift check | ✅ (if §9 adopted) |

### E5. Shipping a new version / release (multi-step example)

A worked example of the "ordered checklist + safety nets" pattern. Adapt names to your project.

| File | Layer | How to update | Symptom if skipped | Backstop |
|---|---|---|---|---|
| Release artifact / summary (JSON) | L1 | Produced by the build/run itself | — (can't ship without it) | — |
| `wiki/<domain>/release_history.jsonl` | L1 | **Append** one row | Derived "current state" view goes stale silently | Nightly drift check comparing git tags vs ledger |
| Production config | L1 | Hand-edit, with version comment | New version not actually live | Post-release verify job |
| `wiki/_current_state.md` (or `CURRENT_*.md`) | L2 | `sync` script regenerates from ledger | Readers see the previous release as "current" | `sync --check` in pre-commit |
| `wiki/experiments/<version>_story.md` | L3 | Hand-write the narrative | The "why" is lost within weeks | — (no net — do it now) |
| `wiki/log.md` + `wiki/index.md` | L3 | One line each | Release invisible to future queries | Lint |
| Long-lived worker processes | runtime | **Restart** | Still running old version; "configured but not in effect" | Next-day consistency check |

**Strict order**: build artifact → append ledger → update config → run sync → write narrative → commit → restart workers → next-day verification.

**Automatic safety nets** (backstops, not replacements): nightly ledger-vs-git drift check (catches skipped append), nightly sync run (catches skipped regenerate), next-day consistency check (catches skipped restart).

## Reverse events (auto-derived — only with SCHEMA §9)

Forward events above answer "an X happened → which files". Reverse events answer "file Y was modified → what must be reviewed". These sections are **generated by the sync script from frontmatter declarations — never hand-write them**:

```markdown
### R1. Core code module changed
<!-- AUTO-GENERATED by sync script from skills' `consumes:` — DO NOT EDIT -->
...list of skills/pages that declared this module as load-bearing...
<!-- /AUTO-GENERATED -->
```

## Forbidden actions

Keep a short explicit list — these are the mistakes the layering exists to prevent:

| Action | Why forbidden |
|---|---|
| ❌ Hand-editing any L2 file (`_current_*.md`, generated summaries) | Next sync run silently overwrites your edit |
| ❌ Copying a number from an L1 ledger into CLAUDE.md / README / narrative | Guaranteed staleness; link instead |
| ❌ Editing a historical row in an append-only ledger | Desynchronizes every consumer; append a superseding row |
| ❌ Creating versioned filenames for stable pages (`thing_v3.md`) | Stale links on every bump; version is a field inside the file |
| ❌ Writing status/deprecation as prose only | Tools can't see prose; use structured markers (SCHEMA §8.6) |

## Appendix: who reads what

Maintain a table of "file → which tools/skills/sessions consume it". Before designing any new consumer, check this table instead of inventing a new file.

| File | Read by |
|---|---|
| `wiki/_current_state.md` (L2) | new sessions, any "what's live now" question |
| `wiki/<domain>/release_history.jsonl` | sync script, release gate, audits |
| exploration ledger | every exploration-type skill (query before starting) |
| `wiki/log.md` | retrospectives, weekly reports |
